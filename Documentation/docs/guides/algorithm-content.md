# Managing algorithm content

Each algorithm's description and ten-language syntax-highlighted code samples live in
`App/Resources/AlgorithmDetails/`, one folder per algorithm ID. A Click CLI, `manage.py`, run
through `uv run`, manages this content. This page covers the everyday workflow. The
[Compression formats](../reference/compression.md) page documents the archive format `manage.py`
produces.

## Layout

Each `<algorithm-id>/` folder holds the authoring source and the finished content side by side:

- Raw reference source: `<algorithm-id>.<ext>` for `ext` in `c cpp cs go java js kt py rb swift`.
- `description.md`, hand-written.
- One `<lang>.md` per language, generated by `manage.py highlight`. These files are gitignored,
  reproducible intermediates. Never edit them by hand.

None of this folder's raw content reaches the app bundle directly. `manage.py pack` compresses
every `description.md` and generated `<lang>.md` into the single `AlgorithmDetails.algz` archive,
which ships as an ordinary app resource. No per-algorithm Tuist build phase exists. Adding a new
algorithm's content means adding its folder here, then running `highlight` and `pack`.

Do not reference any porting source, ArrayV or otherwise, in the reference implementations or in
`description.md`. This content ships as this project's own original reference material.

## First-time setup

```sh
cd App/Resources/AlgorithmDetails
uv run manage.py setup
```

This command installs every Homebrew-installable dependency `test`, `lint`, and `format` need:
lint and format add-ons (`clang-tidy`, `ktlint`, `checkstyle`, `google-java-format`, `ruff`,
`eslint`, `prettier`, `swiftformat`, `swiftlint`) and each language's base compiler or runtime
Homebrew provides (`go`, `java`, `node`, `kotlin`, `ruby`, `dotnet`, plus the `standard` Ruby gem).
It excludes Swift's and C/C++'s own compilers, since Xcode's Command Line Tools already provide
them and are required to build this repository. The command is safe to re-run.

## Adding or editing one algorithm's content

```sh
cd App/Resources/AlgorithmDetails
uv run manage.py scaffold <algorithm-id>       # creates <algorithm-id>/ from template/
# hand-write <algorithm-id>/description.md and the 10 language source files
uv run manage.py test <algorithm-id>           # compiles/runs every language, checks sorted output
uv run manage.py lint <algorithm-id> --fix     # per-language linters
uv run manage.py format <algorithm-id>         # per-language formatters
uv run manage.py highlight <algorithm-id>      # REQUIRED before pack — generates <lang>.md files
uv run manage.py pack                          # rebuilds AlgorithmDetails.algz for ALL algorithms
uv run manage.py decode <algorithm-id>         # optional: sanity-check the packed byte layout
```

Rules for ordering and scope:

- Run `highlight` before `pack`. `pack` compresses only `description.md` and the already generated
  `<lang>.md` files; it never touches the raw `.{c,cpp,...}` sources directly. Skipping
  `highlight` after editing a source file ships stale or missing content.
- `pack` always operates on the whole corpus, not just the algorithm you edited. Running it after
  one change regenerates `AlgorithmDetails.algz` for every algorithm. This is expected: the
  archive is one whole-corpus zstd frame, not per-algorithm files (see
  [Compression formats](../reference/compression.md) for the reason). Commit the resulting single
  binary diff after any content edit.
- `lint --fix` and `format` re-verify against `test` automatically. If an autofix breaks a file,
  the command restores the original. This safety net is not optional; an automated fix has caused
  a real regression in this repository before. Both commands require `setup` to run first.
- `test`, `lint`, and `format` default to every algorithm and every language. Use `-l py -l js` and
  similar flags to restrict languages. Pass one or more `<algorithm-id>` arguments to restrict
  algorithms.
- `format` also creates a persistent, gitignored `<file>.swift.bak` backup for Swift files before
  every pass. Every `swiftformat` invocation runs serially, one at a time, regardless of how many
  algorithms are being processed concurrently. This responds directly to a past incident: running
  the Swift formatter across many files in parallel produced non-deterministic file corruption in
  this repository.

## Regenerating after a content edit

Once you know what changed, run:

```sh
cd App/Resources/AlgorithmDetails
uv run manage.py highlight && uv run manage.py pack
```

`pack` self-verifies by default after writing. It reads the archive back, decompresses and
checksum-verifies it, parses it with an independent Python reference parser, and byte-compares
every extracted range against the source `.md` files on disk. `--no-verify` skips this check; do
not use it as a default.

## Parallelizing across many algorithms

Writing all ten languages for several algorithms in parallel — for example, across several
background agents — works cleanly as long as each agent owns exactly one algorithm's folder. No
file conflicts occur, even without special isolation, because the shared files (the three
registration call sites from [Adding a sorting algorithm](adding-an-algorithm.md), and the port
tracker) are edited only by whoever orchestrates the batch, never by the per-algorithm work
itself.

## Binary conflicts

`AlgorithmDetails.algz` cannot be three-way merged; it is compressed binary. Two branches that
both touched content will show a `Bin XXX -> YYY bytes` diff with no meaningful merge. The recovery
path is always the same: regenerate from the still-tracked `description.md`/source files on your
branch (`highlight` then `pack`) and recommit. Do not attempt to merge the binary directly.

See `App/Resources/AlgorithmDetails/README.md` for the complete `manage.py` command reference,
including `decode`'s full output format and the one known gap: `lsdradixsort/` ships without raw
source behind it.
