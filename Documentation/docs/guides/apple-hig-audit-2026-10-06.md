# Apple Human Interface Guidelines audit

**Date:** 2026-10-06

**App:** Sort Symphony, iOS and iPadOS with Mac Catalyst
**Status:** Comprehensive review of the primary product journeys. This is a design and accessibility findings report, not a certification that every assistive technology and device configuration has been manually exercised.

## Answer to the earlier question

No complete HIG audit had been done before this report. The earlier [accessibility and design working findings](accessibility-design-audit-2026-10-06.md) fixed several issues and covered selected Dynamic Type and accessibility-tree checks. It explicitly left the full HIG and manual VoiceOver review open.

## Method and scope

I compared Apple's current HIG with the shipping SwiftUI views and their interaction code, the existing iPad and Catalyst UI-test evidence, and a live Mac Catalyst pass through navigation, a completed sort, the accessibility tree, the visible sort layout, and Settings. The live app was the existing local Debug Catalyst build at `/private/tmp/sort-accessibility-derived/Build/Products/Debug-maccatalyst/SortSymphony.app`, built from the current `dev` work. I inspected the behavior of Home, the category sidebar and algorithm list, search and sort menu, the sort canvas and transport, algorithm details and charts, Settings, file import/export, and the long-running automation surfaces. Platform-specific behavior is identified where it differs.

Evidence keys below: **Observed** = seen in the live Catalyst UI or accessibility tree; **Code** = directly present in source; **Test** = covered by existing automated verification; **Open** = needs a person to check the experience or a configuration not exercised here. A code-level risk is not labeled a reproduced visual failure. HIG guidance is contextual: a different implementation can still satisfy the user need.

The review does **not** include listening to VoiceOver on an iPad or Mac, Voice Control, Switch Control, a physical iPad keyboard, systematic color contrast measurements for every visualizer, or a full matrix of iPad window sizes, languages, and appearance settings. Those remain explicit verification tasks below.

## Executive assessment

The application's basic structure fits Apple's idioms well: a three-level split view for category → algorithm → detail; native lists, search, menus, forms, sliders, sheets, file panels, and a Mac menu bar; visible playback state and recoverable errors. The transport now has unusually good spoken labels and values for a custom visualizer. The largest remaining differences are concentrated in the custom experience: the Metal canvas still conveys only a static summary to nonvisual users, the Catalyst top toolbar uses symbol descriptions instead of action names, charts have partial exploration support, and the app's Dynamic Type and compact-window coverage is incomplete. The long Home explanation and powerful but obscure toolbar automation actions also make first use harder than Apple's guidance suggests.

## Recommended order

1. **Name the top toolbar actions** for speech and hover, including distinct Start/Stop Showcase and Start/Stop Full Sweep labels. This is a reproduced, localized defect.
2. **Finish the iPad large-text and compact-window matrix.** Reproduce the sidebar clipping at accessibility sizes; traverse Home → category → search → sort → Settings and expanded charts in portrait, half-width, and minimum-width windows.
3. **Validate the scoped sorting accessibility path.** Test the existing manual-step speech with VoiceOver and keep the canvas's static summary honest. Do not queue spoken announcements for every automatic operation.
4. **Review custom motion and color.** Try Reduce Motion, Differentiate Without Color, Increase Contrast, light/dark modes, and color filters across representative visualizers. Preserve Metal easing; evaluate a playback cap and mode-specific choices only where testing shows a problem. Add noncolor cues only where an essential distinction is otherwise lost.
5. **Improve chart exploration.** Provide a plain-language chart takeaway, meaningful series/value labels, and a keyboard-accessible route to exact values. Verify the expanded chart with VoiceOver and Switch Control.
6. **Keep Home as the first-run context.** Make a low-pressure example action easy to find, then teach speed, size, steps, and chart details contextually, potentially with TipKit.
7. **Complete platform checks.** Test physical iPad keyboard and system audio behavior; plan string extraction and a right-to-left layout pass if localization is in scope.

## Action plan from the 2026-10-06 review

This plan reflects the owner's decisions after reviewing the findings. The first step of each work item is to confirm behavior in the app; implementation follows only where the stated acceptance condition fails. Keep the existing Home introduction, three-column structure, full-sized animated title, Metal easing, and details below the visualization. No new inspector or details sidebar is proposed.

### Shared rule: accessibility and test identifiers

Every changed or newly introduced **interactive** control, meaningful status, chart summary, tip, and error state gets a stable, unique `accessibilityIdentifier` on the element users actually reach. Preserve existing identifiers and add missing ones to production UI, not just debug probes. Known starting gaps to check include the Home title button, catalog search field, Settings Done button, Copy Code button, expanded-chart previous/next buttons, and algorithm-row context-menu actions. An identifier is not a spoken label: check the label, value, hint, trait, enabled state, and focus order separately. Use stable names based on purpose (`showcaseButton`, `growthModelSummary`, `codeSampleReadFullButton`), with a stable algorithm or series key only when repeated elements need disambiguation. Avoid indices, localized text, transient values, and individual Metal bars as identifier keys. For each touched journey, add a focused UI assertion that locates the element by identifier **and** checks the relevant user-visible or spoken result. Finish with a source inventory of primary screens and a live accessibility-tree pass so future UI tests can rely on the identifiers without reshaping the interface.

**Algorithm icons:** `CustomIconLabel` pairs each SF Symbol with the algorithm's visible name. In the live Catalyst tree, the row is one button named for the algorithm, with no extra symbol announcement. The icons are decorative mnemonics, not a second data channel, so they need no per-icon label or identifier. Assert the combined row name in UI tests; if a future icon represents an independent state, give that state a text or accessibility equivalent then.

### C. Sorting-specific accessibility, color, motion, and sound

7. **Scope the VoiceOver promise to what is useful.** Test the current canvas summary, scrub value, and manual forward/back/jump speech with VoiceOver and focus navigation. Preserve the decision to speak only a user-requested step, not every operation in an automatic run. Check whether a concise static summary (algorithm, size, visualizer, current position/status) improves the experience without implying complete nonvisual parity with the visual animation. Document any inherent limitation honestly. **Done when:** a VoiceOver user can locate, control, pause, step, and understand the run's coarse state without a speech backlog. Do not add a runtime generated narration requirement.
8. **Marker semantics before expanding colors.** Inventory the meaning of every marker/operation across all built-in visualizers, then check whether distinct states are actually distinguishable in light, dark, Increase Contrast, Differentiate Without Color, and common color filters. Start by assigning consistent **semantic** colors to a small set of meaningful marker roles; do not require one unique color for every recorded operation or create a bespoke palette merely to exhaust possible states. Where two essential roles are still indistinguishable, test an existing shape, position, outline, line style, or small legend before a renderer-wide redesign. System colors can adapt UI chrome, but custom Metal pixels do not automatically acquire new semantic meaning when a color-vision setting changes; Apple's [Differentiate Without Color criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/differentiate-without-color-alone-evaluation-criteria/) call for an additional cue when color alone carries the distinction. **Done when:** the audit identifies which distinctions are essential and verifies those distinctions without relying solely on hue, or records a precise, visualizer-specific limitation.
9. **Reduce Motion without removing shader easing.** Preserve the Metal easing and interpolation. Measure how a real run feels with Reduce Motion enabled, then cap automatic playback speed for that mode while keeping manual stepping and the user's normal-mode speed intact. Evaluate high-motion visualizers such as Hanoi Towers individually; if a particular presentation remains uncomfortable, offer a calm default or omit that visualizer from automatic selection in Reduce Motion mode, with an explicit path to choose it manually. Do not conflate this visualizer with HanoiSort. Verify that the existing title behavior continues to remove spatial swap motion. **Done when:** Reduce Motion yields a visibly calmer automatic run, settings are clear, and ordinary playback keeps its current smoothness.
10. **Audio behavior.** Verify silent mode, other-audio mixing, headphones connect/disconnect, interruption, app background/foreground, and Catalyst Audio Unit routing on devices that support each path. ### E. Cross-platform audit and localization

15. **Catalyst toolbar labels.** Add explicit `accessibilityLabel` and `.help` to Import Tape, Settings, Showcase, and Full Sweep. 16. **Dynamic Type everywhere feasible.** Run Xcode's Dynamic Type and clipping audits at regular and accessibility sizes on Home, sidebar/catalog, sort controls, Settings, chart sheets, empty/error states, import/export, and tips. Inspect the actual UI at compact and wide sizes because an automated warning can come from a system List row. Prefer wrapping, reflow, shorter visible copy, or `ViewThatFits` over shrinking fonts. Keep semantic text styles, and preserve the deliberate large title. **Done when:** every primary action and required explanation stays readable and reachable, or a platform false positive is captured and explained.
17. **Full Keyboard Access and VoiceOver outside the canvas.** Traverse every primary journey with the system feature actually enabled, not only through the accessibility tree: category/list search, sort and its disclosures, Settings, confirmation dialogs, expanded charts, import/export, and tips. Check focus order and return focus after dismissal. Check the chart's exact-value route and code disclosure with keyboard only. Use the existing Catalyst menu shortcuts as a baseline; verify a physical iPad keyboard when available. **Done when:** the same tasks can be completed without touch and without guessing controls from icons.
18. **String catalogs and right-to-left layout.** The product modules target **iOS 18.0** (`Tuist/ProjectDescriptionHelpers/Module.swift`), while Foundation Models starts at iOS 26 and also depends on device/model availability; runtime generation is therefore a poor dependency for interface copy. Apple's current [string catalogs](https://developer.apple.com/documentation/xcode/localizing-and-varying-text-with-a-string-catalog) are a substantial improvement over hand-maintained `.strings`: Xcode extracts most SwiftUI literals, supports interpolation, plurals, device variants, comments, and generated symbols. We do **not** have to hand-write `%@` for every input. First add catalogs to the Tuist source of truth and audit which strings extract from each module; convert dynamic UI prose and the Home Markdown to explicit localizable resources as needed. Keep algorithm names and source-code samples deliberately classified instead of blindly translating them. Then run Xcode's [double-length and right-to-left pseudolanguages](https://developer.apple.com/documentation/xcode/preparing-your-interface-for-localization), fix directional icons/alignment and truncation, and choose one real language for a reviewed pilot. Xcode now documents [agent-assisted translation](https://developer.apple.com/documentation/xcode/localizing-your-app-using-agents), but any generated text still needs contextual review and in-app testing. **Done when:** the catalog contains all intended UI strings, interpolated/plural values read correctly, pseudo-RTL navigation and charts remain usable, and the pilot language is reviewed by a fluent reader before release.

### Suggested implementation sequence

**Batch 1: reproducible, small fixes.** Toolbar action names and their identifiers/tests; sidebar/badge/automation/target checks; large-text and compact-window reproduction. This establishes a trustworthy UI baseline.

**Batch 2: teach and explain.** Optional Home example, TipKit or scroll cue, deterministic growth and recorded-run summaries, legends, expanded-sheet sizing, and on-demand code reading. Chart summaries should share data sources with the charts so they cannot drift.

**Batch 3: system accommodations.** Color/marker inventory, Reduce Motion speed cap and visualizer review, full keyboard/VoiceOver passes, and audio verification. Make renderer changes only for distinctions that testing shows are lost.

**Batch 4: localization foundation.** String catalogs and extraction, pseudolanguage fixes, then one reviewed language. Keep this separate from chart narration and app-time Foundation Models.
