Status: planning document; the Python-side tooling (`App/Resources/AlgorithmDetails/manage.py`,
including the `pack` subcommand that implements the ALGZ v1 container spec below and self-verifies
against it) is implemented as a preparatory side-project — see Migration plan, below, for exactly

(§2A.6, "what's still open"). This doc covers two independent efforts:

1. Replacing the current plain-text `AlgorithmDetails/**/*.md` resources (per-algorithm,

2. An effort analysis of the five Phase 12 stretch goals, for scoping/sequencing a future pass.

**Part 1 supersedes all earlier compression-plan drafts.** It folds in a follow-up review

## Part 1: Zstandard compression for AlgorithmDetails

### Why, restated

`App/Resources/AlgorithmDetails/` currently ships 1,180 tracked files (~17.36 MB) — 108
algorithms × (1 `description.md` + 10 per-language `.md` files generated by `manage.py highlight`'s
Pygments tokenizer). The generated `.md` files use a verbose `^[text](code: 'Token.X')` markdown
syntax that Foundation's `AttributedString(markdown:)` parses directly via `CodeAttributes`
(`Modules/DesignSystemKit/Sources/CodeAttributes.swift`) — every space becomes a 30+ byte span, so
the format inflates ~12-20x over raw source. This costs twice: ~17 MB in every build (loaded
per-algorithm at runtime by `AlgorithmDetailContent.load(for:)`,
`Modules/SortFeature/Sources/AlgorithmDetailContent.swift`, shipped via 108 per-algorithm
`CopyFilesAction`s from `Module.algorithmDetailCopyFiles()` in
`Tuist/ProjectDescriptionHelpers/Module.swift`); and thousands of changed text lines in git on
every algorithm-content edit, bad enough to already need a `.gitattributes` `linguist-generated`
workaround once.

### Authoritative measurements

These are the measured figures the whole plan is built on — treat them as source of truth over
any earlier estimate:

| Approach | Total size | Ratio |
|---|---:|---:|
| Whole-corpus, single frame, no dictionary | 290,961 B | 59.7:1 |
| Per-algorithm frames, no dictionary | 570,142 B | 30.5:1 |
| Per-algorithm + 16 KB trained dictionary | 543,604 B | 31.9:1 |
| Per-algorithm + 32 KB trained dictionary | 497,267 B | 34.9:1 |
| Per-algorithm + 64 KB trained dictionary, best found | 481,108 B | 36.1:1 |
| Per-algorithm + 64 KB naive raw-content dictionary | 530,089 B | 32.8:1 |
| Per-algorithm + ~46–57 KB auto-sized trained dictionary | 562–576 KB | ~30–31:1 |

Resolved conclusions:

- The **59.7:1 result does not require a dictionary** — it's the whole 17.36 MB corpus compressed
  as one zstd frame, full stop. Do not describe it as dictionary-assisted.
- One whole-corpus frame beats every per-algorithm configuration measured, including
  per-algorithm-plus-trained-dictionary. Per-algorithm framing was only ever attractive for the
  git-diff-isolation property, which is moot for a single-contributor repo (see below).
- `AlgorithmDetails.algz` v1 therefore uses **one whole-corpus zstd frame, no dictionary**.
- Any future proposal to add a dictionary to this archive must compare its **complete stored
  size** — dictionary bytes plus container overhead included — against the 290,961 B baseline
  above, not just the compressed-payload delta.
- `ZstdKit` still implements dictionary support as a generic decoder capability (useful for other,
  future archives), but it is explicitly **not required** by `AlgorithmDetails.algz` v1 and must
  not block the first application integration.

### Decision: one combined archive, not per-algorithm files

Single contributor, no concurrent-PR merge-conflict exposure to worry about — so the earlier
per-algorithm-file design (chosen specifically to isolate git diffs between concurrent PRs) is
unnecessary caution here. A single archive wins outright once that constraint is off the table:

- **Compression**: per the measurements above, a single zstd frame spanning the whole 17.36 MB
  corpus hits 59.7:1 vs. 30.5:1 for independent per-algorithm frames and no better than 36.1:1 even
  with a well-tuned per-algorithm dictionary — because the whole corpus fits comfortably inside
  zstd's window, so cross-algorithm redundancy (the same token-type vocabulary repeating across all
  108 algorithms) compresses away for free, no dictionary machinery needed.
- **Project simplification**: `Module.algorithmDetailCopyFiles()`'s 108-`CopyFilesAction`
  generation (one per algorithm, required today only because per-language files needed per-folder
  destinations) collapses entirely into **one** ordinary resource entry. This is a real Tuist
  manifest simplification, not just a compression win.
- **Content scope**: the archive holds *everything* — all 10 language samples **and** all 108
  `description.md` prose files. There's no remaining reason to keep descriptions separate once
  per-algorithm diff isolation isn't a goal; folding them in adds negligible size (prose is small
  relative to the token-expanded code samples) and removes the last loose text files from
  `AlgorithmDetails/`'s shipped output entirely — while the canonical `description.md` sources stay
  tracked in git regardless (see Git migration below; the archive is a derived bundle resource, not
  the source of truth).

**Accepted tradeoff, explicitly**: every future algorithm-content edit changes the same one binary
file. `git diff --stat` collapses to a single `Bin XXX -> YYY bytes` line regardless of which
algorithm changed (you lose the "which algorithm" signal from the diff itself, though the commit
message still carries it), and two branches both touching content can't be 3-way merged — git will
flag a binary conflict and either side has to be picked, with "regenerate the archive from the
still-tracked source files and recommit" as the reliable recovery path. Fine for a
single-contributor repo; would be reconsidered if this project ever gained concurrent contributors
regularly touching algorithm content in parallel.

### Container format

**This section replaces the first draft's container format entirely.** The first draft proposed a
single manifest living inside the decompressed payload with no framing beyond that; its prose and
its `manage.py pack` sketch didn't fully agree on whether all headers preceded all content, so the review
treats that ambiguity as unresolved and replaces it with an explicit, versioned, two-level
structure: an **outer envelope** living outside the zstd frame, and an **inner payload header**
living inside it (post-decompression). The outer envelope is new — it's what makes the format
independently versionable, lets a future dictionary or codec change be added without breaking v1
readers, and carries an integrity check (SHA-256) that covers the whole decompressed payload
independent of zstd's own checksum.

One file, `App/Resources/AlgorithmDetails/AlgorithmDetails.algz`. All multibyte integers anywhere
in `ALGZ` are **unsigned little-endian**. The manifest parser reconstructs them from raw bytes
(`UInt32(b0) | UInt32(b1) << 8 | ...`) or a small audited safe-reader helper — never an aligned
typed load without a preceding bounds check.

#### Outer envelope (outside the zstd frame)

| Field | Type | Meaning |
|---|---|---|
| Magic | 8 bytes | `41 4C 47 5A 0D 0A 1A 0A` (`ALGZ` + CR LF SUB LF, mirrors PNG's corruption-detecting magic) |
| Major version | `UInt16` | Breaking format version (`1` for v1) |
| Minor version | `UInt16` | Backward-compatible revision |
| Header length | `UInt32` | Total outer-header byte length, including any extension bytes |
| Flags | `UInt32` | Declared optional features (see below) |
| Codec | `UInt16` | `1` = Zstandard |
| Reserved | `UInt16` | Must be zero in v1 |
| Dictionary offset | `UInt64` | Zero when absent (always zero in v1) |
| Dictionary length | `UInt64` | Zero when absent (always zero in v1) |
| Frame offset | `UInt64` | Absolute byte offset of the zstd frame |
| Frame length | `UInt64` | Exact compressed frame length |
| Decompressed length | `UInt64` | Expected complete payload length |
| Payload SHA-256 | 32 bytes | Digest of the full decompressed payload |
| Extension bytes | variable | Skipped per `Header length`, reserved for future fields |

Flags (v1):

```text
bit 0: embedded dictionary is present
bit 1: embedded dictionary is a standard formatted Zstd dictionary
bit 2: payload SHA-256 is present and required
all remaining bits: reserved
```

For v1: no dictionary (bits 0/1 clear, offset/length zero), bit 2 set (SHA-256 always present and
checked), zstd content checksum enabled inside the frame itself. An unknown *required* flag (a bit
the reader doesn't recognize but the format says must be honored) is a clean unsupported-format
error, never a silent skip; unrecognized bits explicitly documented as safe-to-ignore may be
skipped.

#### Inner payload header (first bytes of the decompressed zstd output)

| Field | Type | Meaning |
|---|---|---|
| Payload magic | 8 bytes | `ADTL` signature (padded/fixed to 8 bytes) |
| Schema major | `UInt16` | Breaking manifest version |
| Schema minor | `UInt16` | Compatible manifest revision |
| Header length | `UInt32` | Inner header length including extension bytes |
| Flags | `UInt32` | Payload features, reserved in v1 |
| Algorithm count | `UInt32` | Number of directory records — the parser must not infer this by scanning to end-of-buffer |
| Directory offset | `UInt64` | Offset from start of decompressed payload |
| Directory length | `UInt64` | Exact directory length |
| Content offset | `UInt64` | Offset from start of decompressed payload |
| Content length | `UInt64` | Exact concatenated content length |
| Reserved/extension | variable | Skipped via `Header length` |

#### Algorithm directory records (one per algorithm, back-to-back within `Directory` range)

| Field | Type | Meaning |
|---|---|---|
| Record length | `UInt32` | Full record length including this header |
| Algorithm ID length | `UInt16` | UTF-8 identifier byte length |
| Entry count | `UInt16` | Number of content entries that follow |
| Algorithm flags | `UInt32` | Reserved, zero in v1 |
| Algorithm ID | variable | Valid UTF-8, e.g. `"quicksort"` |
| Content entries | variable | Fixed-size records, see below |
| Extension bytes | variable | Skipped via `Record length` |

Algorithm IDs must be nonempty, valid UTF-8, unique, deterministically sorted by the packer
(stable ID sort — the same input tree always produces byte-identical output), and compared as
exact byte/string identifiers with no Unicode normalization.

#### Content entries (fixed-size, inside each directory record)

| Field | Type | Meaning |
|---|---|---|
| Content kind | `UInt16` | See table below |
| Entry flags | `UInt16` | Optional/required + reserved future bits |
| Content offset | `UInt64` | Relative to the start of the content section |
| Content length | `UInt64` | Byte length |
| Reserved | `UInt32` | Must be zero in v1 |

Content-kind IDs (stable once v1 ships):

| ID | Kind |
|---:|---|
| 0 | Description Markdown |
| 1 | Python highlighted Markdown |
| 2 | JavaScript highlighted Markdown |
| 3 | Go highlighted Markdown |
| 4 | Java highlighted Markdown |
| 5 | C highlighted Markdown |
| 6 | C++ highlighted Markdown |
| 7 | C# highlighted Markdown |
| 8 | Ruby highlighted Markdown |
| 9 | Kotlin highlighted Markdown |
| 10 | Swift highlighted Markdown |

A missing optional language is represented by an **absent** content-entry record (not a
zero-length one) — this preserves today's "file doesn't exist for this language" semantics rather
than conflating it with "file exists and is empty." Unknown optional content kinds are skippable
via the fixed entry size; unknown required content kinds are an unsupported-format error.

#### Content section

The exact concatenation of every entry's UTF-8 bytes, in this deterministic order: algorithms
sorted by stable algorithm ID, then within each algorithm description first, then languages sorted
by stable numeric content-kind ID. All content-entry offsets are relative to the start of this
section. The manifest (payload header + directory) and the content section must not overlap.

This custom manifest, not tar, remains the right call for the inner format — it avoids ustar's
512-byte header blocks, octal ASCII size fields (a parser of their own, not binary integers), a
self-referential checksum field, PAX/GNU extensions, symlink/hardlink/device handling, and
path-traversal concerns, none of which this fixed, self-contained domain needs. The custom
envelope/manifest parser is implementable with ordinary bounds-checked Swift; unsafe code is
reserved for the optimized zstd decoder core, not this parsing layer.

### UTF-8 handling

Every byte range the manifest describes is guaranteed UTF-8 by construction — `manage.py highlight` and
`description.md` both originate as UTF-8 text, and `manage.py pack` never touches the bytes, just
concatenates and compresses them. Manifest offsets and lengths are **byte** offsets and lengths,
never character, Unicode-scalar, or `String.Index` values.

The packer validates UTF-8 before compression. The Swift loader validates it again in release
builds using the non-repairing initializer:

```swift
guard let text = String(validating: bytes, as: UTF8.self) else {
    throw AlgorithmDetailsArchiveError.invalidUTF8
}
```

**Correction from the first draft**: do not use `String(decoding:as:)` for archive loading — it
silently substitutes U+FFFD for invalid bytes, which would violate the requirement that loaded
strings be byte-identical to the generated resources. `String(decoding:as:)`'s appeal in the first
draft was "no defensive fallback logic needed since both ends are code we control" — true in
spirit, but the non-repairing initializer costs nothing extra and turns a `manage.py pack`/Pygments
regression into a loud decode-time error instead of a silently corrupted code sample shipped to
users. No runtime normalization is performed either way: source bytes, line endings, Unicode
scalars, and Markdown syntax are preserved exactly as generated.

### Safety model

**Correction from the first draft**: the first draft proposed catching manifest/bounds
inconsistencies with debug-only `assert()` (compiled out in release, on the theory that `manage.py pack`
and the Swift decoder are both code we control, not an untrusted-input boundary). That's
superseded — every structural and memory-safety condition below must be a **throwing check in
release builds**, not an `assert`/`precondition`/debug-only check:

- Buffer bounds, integer conversions, integer addition/multiplication, allocation sizes, offsets,
  and lengths.
- Manifest self-consistency (entry-length sums match total decompressed size, algorithm count
  matches the directory, no overlapping records).
- Dictionary IDs, frame/window limits, UTF-8 validity, checksums, duplicate algorithm IDs,
  duplicate content kinds per algorithm, unsupported versions/flags.

Rationale: "both ends are code we control" protects against a *malicious* input, which is true,
but it doesn't protect against a `manage.py pack` regression shipping a malformed archive that a debug
build never caught and a TestFlight/release build then silently mis-slices or overruns on. Debug
assertions may duplicate these checks to catch programmer error earlier, but they are never the
*only* enforcement.

Overflow-safe range-check pattern (do not validate with `offset + length <= count` before
separately proving the addition can't overflow):

```swift
guard offset <= buffer.count else { throw Error.outOfBounds }
guard length <= buffer.count - offset else { throw Error.outOfBounds }
```

Convert every `UInt64` field to `Int` with `Int(exactly:)`, never a truncating cast.

Explicit, configurable resource limits, sized comfortably above the measured ~17.36 MB corpus but
low enough to reject absurd or corrupted declarations:

```swift
public struct ZstdDecodingLimits: Sendable {
    public var maximumOutputSize: Int
    public var maximumWindowSize: Int
    public var maximumDictionarySize: Int
    public var maximumBlockCount: Int
    public var maximumFrameSize: Int
}
```

Zero C/C++ interop remains a hard requirement. Scoped Swift unsafe APIs
(`withUnsafeBytes`/`withUnsafeMutableBytes`, `UnsafeRawBufferPointer`/`UnsafeMutableRawBufferPointer`,
unaligned loads after explicit bounds checks) are acceptable for performance, but only:

- Internal to `ZstdKit` — never in the outer `ALGZ`/manifest parser, which stays safe Swift unless
  profiling proves otherwise.
- Small and auditable, each one documented with the invariant that makes its load/store valid.
- Protected by release-mode range validation before the unsafe access, not after.
- Covered by scalar differential tests and, where available, sanitizers (ASan/UBSan).

### Encoder: Python, not Swift

No new Swift build tool for encoding — `ZstdKit` is explicitly **decode-only** (see below). The
existing manual pipeline (`App/Resources/AlgorithmDetails/README.md`'s `manage.py` CLI, covering
`scaffold`/`highlight`/`test`/`pack` as one tool sharing a single algorithm-discovery/logging
setup — done as a preparatory side-project ahead of `ZstdKit` itself) already implements `pack`
using the `zstandard` PyPI package. Run as `uv run manage.py highlight && uv run manage.py pack` —
still fully manual, matching the existing workflow exactly (no CI/Xcode Cloud changes; this
pipeline was never invoked from CI).

Compression settings for `AlgorithmDetails.algz` v1:

- One whole-corpus frame, zstd level 19 unless a fresh benchmark supports another level.
- No dictionary; dictionary ID field is irrelevant.
- Content size enabled (`write_content_size=True`).
- **Zstd content checksum enabled** (`write_checksum=True`).
- Deterministic single-threaded compression (`threads=0`) unless testing proves a multithreaded
  mode is deterministic across the pinned environment.
- Standard frame magic, no magicless mode, no skippable frames, no concatenated frames, no
  long-distance-matching override without a measured improvement.

```python
compressor = zstandard.ZstdCompressor(
    level=19,
    write_checksum=True,
    write_content_size=True,
    threads=0,
)
frame = compressor.compress(payload)
```

**Correction from the first draft**: the first draft set `write_checksum=False` specifically to
avoid needing an XXH64 implementation in the Swift decoder, reasoning the checksum was "redundant
with git/bundle integrity guarantees we already have." That reasoning doesn't hold once the
decoder is meant to be a general, standards-compliant `ZstdKit` rather than a narrow
single-archive reader — a real zstd decoder needs to support checksummed frames regardless (they're
common in the wild), so there's no actual implementation cost avoided, only a verification layer
lost for zero savings. v1 enables the checksum, and `ZstdKit` implements and requires it.

Reproducibility: pin the Python version range, `zstandard` package version, Pygments version, and
any other generation dependency — already done via the checked-in `pyproject.toml`/`uv.lock` pair
(`uv add`/`uv remove`, never hand-edited) — alongside the compression level, threading
configuration, input ordering, newline behavior, and the format/content-kind version numbers
above. Do not auto-retrain a dictionary during ordinary regeneration —
if dictionary support is ever adopted for this archive, training is an explicit maintenance
operation with the resulting bytes committed and versioned, not a side effect of a normal
`manage.py pack` run.

`manage.py pack` must fail before compression if: a required hand-authored description is missing, a
canonical `manage.py highlight` input can't be found, a generated highlighted Markdown file is malformed,
any text file isn't valid UTF-8, an algorithm ID or content kind is duplicated, any length exceeds
its integer field width, or the manifest can't represent the complete payload. After writing the
archive, `manage.py pack` immediately self-verifies by default (`--no-verify` opts out): read the
archive back, verify the outer header and SHA-256, decompress with `python-zstandard` (which
verifies the zstd checksum as part of decompression), parse the manifest with a Python reference
parser, and compare every extracted byte range against its source file. Shelling out to the
standard `zstd` CLI as a second decoder oracle was left out of the first implementation as
optional extra credit, not a requirement.

### Decoder: pure-Swift Zstd, decode-only

New module, `Modules/ZstdKit/` — generic, app-agnostic, and **decode-only as a hard design
constraint**, not just an unimplemented feature:

```swift
public enum Zstd {
    public static func decompress(
        _ frame: Data,
        using dictionary: ZstdPreparedDictionary? = nil,
        limits: ZstdDecodingLimits = .default
    ) throws -> Data

    public static func prepareDictionary(
        _ dictionary: Data,
        limits: ZstdDecodingLimits = .default
    ) throws -> ZstdPreparedDictionary
}
```

No `compress` API, no encoder stub suggesting eventual symmetry, no match finder/optimal parser/
Huffman encoder/FSE encoder, no Swift-side dictionary trainer. If dictionary support is staged
after the first integration, the first shipped API may omit the `using:` parameter, but the
internal design must not make dictionary history or dictionary-provided entropy tables impossible
to add cleanly later. Compression stays the Python pipeline's job, permanently — cutting encoding
isn't a shortcut on work we'd do eventually; a real zstd encoder's match-finding and from-scratch
entropy-table construction is arguably more work than decoding, and is permanently unnecessary here
since Python already does it well.

**Correction/expansion from the first draft**: the first draft scoped the decoder narrowly enough
that it risked correctness depending on "what level 19 happens to emit." The decoder must support
every normal encoding a standard compressor may produce, not just the subset our own `manage.py pack`
happens to use:

- **Frame support**: standard zstd magic, frame header descriptor, single-segment and ordinary
  windowed frames, every valid frame-content-size field width, window descriptor parsing,
  dictionary ID fields, content checksum flag, reserved-bit validation, exact frame-content-size
  validation when present, configurable maximum output/window sizes. The first public operation may
  require exactly one standard frame and explicitly reject concatenated frames, skippable frames,
  legacy formats, and magicless format with specific unsupported-format errors (never misclassified
  as generic corruption).
- **Block support**: raw, RLE, and compressed blocks; reject reserved block type 3.
- **Literals support**: raw, RLE, Huffman-compressed, and treeless (previous-table-reusing)
  literals; both directly-encoded and FSE-compressed Huffman weights; one-stream and four-stream
  Huffman literals.
- **Sequence support**: zero-sequence blocks, all valid sequence-count encodings, the three symbol
  streams (literal lengths, offsets, match lengths) in Predefined/RLE/FSE_Compressed/Repeat mode,
  normalized-count parsing, FSE table construction, baseline+extra-bit tables, the three repeat
  offsets including the literal-length-zero swap special case, cross-block history references,
  overlapping match copies, and exact sequence-bitstream termination validation.
- **Dictionary support** (generic `ZstdKit` capability, not required by `AlgorithmDetails.algz`
  v1): raw-content dictionaries, standard formatted zstd dictionaries, dictionary magic/ID,
  dictionary-provided Huffman/LL-FSE/offset-FSE/ML-FSE tables, dictionary-provided initial repeat
  offsets, dictionary history content, and frame-dictionary-ID matching. **A trained dictionary is
  not just raw bytes prepended to output history** — it also carries pretrained entropy tables and
  initial repeat offsets; don't build (or describe) dictionary support as if it were only the
  history-bytes part. If shipping this in the first release would materially delay the application
  migration, it's a separately testable milestone, not a reason to weaken the decoder's internal
  architecture around it.
- **Checksum support**: implement and require zstd's XXH64 content checksum for the generated
  archive. Test XXH64 independently against known vectors first, then against frames emitted by
  Python and the standard zstd implementation. A checksum mismatch is a release-mode error.

Recommended build order, staged so there's a working, testable decoder at each milestone: (1) frame
+ block shell (raw/RLE blocks) against a small hand-built single-algorithm fixture; (2) Huffman
literals (single-table, then treeless); (3) FSE-coded sequences — the hard part: table construction
from normalized counts, backward-read interleaved-state bitstream decode; (4) sequence execution /
LZ77 window sized to the frame's declared content size up front (known because the encoder leaves
`Frame_Content_Size` enabled), not grown dynamically; (5) checksum (XXH64) wired in and tested. Get
1–5 correctness-checked byte-for-byte against Python's `zstandard.decompress()` output before
wiring anything into `AlgorithmDetailContent`, then move to the optimized path (below) once you have
a real decode-time measurement to justify it against.

### Performance strategy

The goal is a fast pure-Swift decoder, not merely a correct academic implementation — but
correctness-first: implement a straightforward scalar decoder and keep it available in tests as the
correctness oracle for every optimized routine that follows.

- **Accelerate is not an architectural dependency.** Zstd decoding is dominated by variable-width
  bit parsing, stateful table transitions, irregular lookups, and overlapping history copies —
  vDSP doesn't naturally accelerate any of that. Benchmark it for a narrow helper only if a concrete
  profile identifies a suitable bulk operation; it must not drive the design.
- **Match-copy performance (wildcopy)**, promoted from optional to a near-term goal once
  correctness is established. Copying `match_length` bytes from an earlier output position is the
  hottest inner loop in any LZ-family decoder; reference `libzstd` vectorizes this (chunked
  8/16-byte copies, plus a doubling trick for short overlapping matches) rather than looping
  byte-at-a-time. Specialize by offset: offset 1 as a byte fill, offset 2 as a repeated two-byte
  pattern, offset 4 as a repeated four-byte pattern, offset 8 as a repeated eight-byte pattern,
  other short overlapping offsets via pattern expansion or carefully validated forward copying —
  and long nonoverlapping matches via machine words or `SIMD8<UInt8>`/`SIMD16<UInt8>` (standard
  library, no C intrinsics), only after benchmarks show an improvement over `UInt64` or ordinary
  buffer copies. Do not use memcpy-like semantics for overlapping matches unless the implementation
  explicitly reproduces the required forward-expansion behavior. This matters more for the
  whole-corpus design than the old per-algorithm one: decompressing ~17 MB once (cached afterward)
  is enough real work that a naive byte-at-a-time loop could be perceptible, while zstd's wildcopy
  trick keeps it fast.
- **Bit-reader optimization**, after the checked scalar reader works: refill from unaligned
  `UInt64` words when enough bytes remain, keep explicit end-of-stream and terminal-bit checks,
  avoid shifts equal to the integer bit width, and retain a checked slow path near buffer
  boundaries.
- **Huffman parallelism**: implement four-stream Huffman decoding as four interleaved scalar states
  for instruction-level parallelism — this, not vector instructions, is genuinely where reference
  zstd's "SIMD" reputation comes from for the entropy stages. Do not claim FSE sequence decoding has
  four equivalent independent streams the same way; it interleaves the literal-length, offset, and
  match-length FSE states inside one single backward bitstream, which is inherently serial.
- **XXH64**: an unrolled scalar implementation first; benchmark grouped/SIMD variants only after
  correctness is fixed.
- **Benchmarking**: on an Apple Silicon Mac and a supported iPad/iPhone-class device (Intel Mac
  only if the project still supports one), separately measure complete archive read, zstd
  decompression alone, manifest parsing, UTF-8 validation/`String` creation, and downstream
  Markdown/`AttributedString` parsing (so decoder performance isn't blamed for that stage), plus
  scalar-vs-optimized match copy, scalar-vs-optimized bit reader, and peak/retained memory. The
  budget favors memory: additional retained memory is acceptable, the real requirement is avoiding
  a visible hitch on first open.

### Runtime: a lazily-decoded singleton

New type, e.g. `AlgorithmDetailStore` (`Modules/SortFeature/Sources/`), replacing
`AlgorithmDetailContent.load(for:)`'s per-algorithm bundle reads:

1. Locate `AlgorithmDetails.algz` via `Bundle.main.url(forResource:withExtension:)`.
2. Parse and validate the outer envelope; validate dictionary fields (v1 expects none).
3. Decompress the single zstd frame via `ZstdKit`.
4. Verify the zstd content checksum, then the declared decompressed length, then the outer
   SHA-256.
5. Parse and validate the inner payload manifest; validate every string as UTF-8.
6. Construct the app's immutable `[String: (description: String, code: [CodeLanguage.ID: String])]`
   model, keyed by algorithm ID.
7. Release the temporary decompressed `Data` buffer once the retained strings exist, unless
   profiling later supports a lazy range-backed design instead.

Loading happens off the main actor. Concurrent callers must share one in-progress load rather than
each decompressing the corpus independently — an actor, or a cached `Task` publishing an immutable
result, is a reasonable shape. Hold the resulting dictionary for the app's session lifetime
(~17 MB resident order of magnitude, negligible on any iPad this app targets — the app already uses
substantially more memory than this archive needs, but measure actual retained size rather than
assuming it's exactly the decompressed corpus size). `AlgorithmDetailContent.load(for:)` becomes a
lookup into `AlgorithmDetailStore.shared` instead of a bundle read — everything downstream
(`AttributedCodeView`, `CodeAttributes`, `CodeTheme`, `MarkdownUI` rendering) is unchanged, since
the strings it receives are byte-identical to today's `.md` files.

### Tuist wiring

`Module.algorithmDetailCopyFiles()` is deleted entirely. Replace its call site in `Project.swift`
with one ordinary resource reference to `App/Resources/AlgorithmDetails/AlgorithmDetails.algz` (the
existing top-level resources glob already excludes `App/Resources/AlgorithmDetails/**` to keep raw

### Error model

Specific public errors, not one generic corruption failure:

```swift
public enum ZstdError: Error {
    case invalidMagic
    case unsupportedFrameFeature
    case unsupportedWindowSize
    case outputLimitExceeded
    case truncatedInput
    case invalidFrameHeader
    case invalidBlockHeader
    case invalidLiteralsSection
    case invalidHuffmanTable
    case invalidFSETable
    case invalidSequenceStream
    case invalidMatchOffset
    case dictionaryRequired(id: UInt32)
    case dictionaryIDMismatch(expected: UInt32, actual: UInt32)
    case checksumMismatch
    case trailingData
}

public enum AlgorithmDetailsArchiveError: Error {
    case invalidMagic
    case unsupportedVersion
    case unsupportedFlags
    case invalidHeader
    case invalidSectionRange
    case hashMismatch
    case invalidManifest
    case duplicateAlgorithmID
    case duplicateContentKind
    case overlappingContent
    case invalidUTF8
    case missingRequiredContent
}
```

Errors carry enough context for diagnostics (offsets, expected vs. actual IDs) without exposing raw
unchecked pointers/offsets to callers.

### Test strategy

- **Zstd decoder fixtures**: small committed fixtures for every frame-content-size encoding,
  single-segment and windowed frames, all three block types, raw/RLE/Huffman/treeless literals,
  direct and FSE-compressed Huffman weights, one- and four-stream Huffman payloads, every FSE table
  mode, repeat tables across blocks, zero-sequence blocks, repeat offsets and the zero-literal
  special case, small/large/cross-block overlapping matches, checksummed and non-checksummed
  frames, raw-content and formatted dictionaries with correct/incorrect IDs, truncated input at
  every structural boundary, reserved bits, oversized declared windows/outputs, and corrupted
  terminal bits/checksums. Use Python `zstandard`, the standard `zstd` CLI, and the official
  `decodecorpus` fixture generator as independent oracles.
- **Differential tests**: every valid fixture decodes identically via the scalar path, the
  optimized path, and the reference implementation. Every invalid fixture is rejected by both Swift
  paths with a stable error category; run under ASan/UBSan where supported.
- **Manifest tests**: empty archive (where allowed), one algorithm, full corpus, unknown optional
  vs. required content kind, duplicate algorithm ID/content kind, invalid UTF-8 in an ID or content
  range, offsets before/beyond the content section, integer-overflow attempts, overlapping regions,
  gaps/trailing content, wrong algorithm count, unsupported major version, extended minor-version
  header, incorrect SHA-256.
- **Application equivalence**, before deleting the old loose-file loading path: load both the old
  files and the new archive, compare every description and highlighted-Markdown string
  byte-for-byte, render a representative set of algorithms in every theme, confirm resulting
  `AttributedString` attributes match, compare startup/first-detail-view performance, and confirm
  the archive is decoded exactly once per session.

### Expected outcome

- Bundle size: ~17.36 MB of `.md` → ~291 KB (`AlgorithmDetails.algz`, whole-corpus zstd level 19,
  no dictionary), a ~98.3% reduction. The outer envelope, SHA-256, and zstd content checksum add a
  small, fixed amount on top of the measured 290,961 B payload — negligible relative to the
  reduction. (Level 22 ultra gets to ~269 KB if ever worth the marginal squeeze — not recommended as
  a default given the added ultra-level window-size handling for ~8% more.)
- Any future algorithm-content edit: `git diff --stat` shows one `Bin XXX -> YYY bytes` line for
  `AlgorithmDetails.algz`, instead of a multi-thousand-line text diff across up to 11 files — while
  the edited `description.md` or canonical source file itself still gets a normal, readable diff,
  since those remain tracked as text.
- Tuist manifest: `Module.algorithmDetailCopyFiles()` and its 108 generated build phases are gone.
- No visible change to the app — verified by spot-checking rendered code views (multiple
  algorithms, all themes) and description text against current `main` before removing the old
  per-file loading path.

### Contingency: if a from-scratch Swift Zstd decoder isn't feasible

If the separate feasibility review comes back negative, fall back to Apple's `Compression`
framework (`Data.compressed/decompressed(using: .zlib)`, i.e. raw DEFLATE per RFC 1951 — confirmed
via Apple DTS, *not* the RFC 1950 zlib-wrapped format some tooling expects, so no cross-platform
readability assumptions). The outer `ALGZ` envelope's `Codec` field exists specifically to make this
swap explicit (`1` = Zstandard would become, say, `2` = DEFLATE) rather than an undocumented format
change; the container format, manifest, singleton store, and Tuist wiring are otherwise unchanged.
The real cost of falling back: raw DEFLATE's fixed 32 KB window means it cannot see redundancy
across the whole 17 MB corpus the way zstd can, so ratio drops from **59.7:1 to 26.6:1** (measured:
290,961 B vs. 652,881 B) — a materially bigger gap here than it was for the old per-algorithm-file
design (~25-27:1 vs. ~28-32:1, a much smaller difference), because the whole-corpus approach is
specifically what benefits from zstd's larger window. Both numbers still represent a huge win over
today's 17.36 MB, so this remains a perfectly viable fallback if needed — just a meaningfully
smaller one.

### Explicitly out of scope

- **Rewriting git history** to reclaim space already spent on currently-tracked `.md` files — this
  plan only stops *future* bloat. History rewrite (`git filter-repo`) is a separate, destructive
  operation; only worth doing on explicit request.
- **Build-time (Xcode Cloud) generation** from raw source — would remove all generated content from
  git permanently, but needs Python+Pygments+zstandard in the Xcode Cloud image for no benefit over
  the existing manual-regen workflow, which this plan doesn't otherwise change.
- **Dictionary support for `AlgorithmDetails.algz` itself**, in v1 or as a near-term follow-up —
  the measurements above show it wouldn't beat the whole-corpus no-dictionary result for this
  corpus. `ZstdKit`'s generic dictionary support (for other, future archives) and this archive's
  format are independent decisions.
- **A Swift-side dictionary trainer** — if a dictionary is ever wanted for some other archive,
  training happens in Python (`zstandard`'s trainer) as an explicit, committed maintenance step,
  never inside `ZstdKit`.

4. ✅ **Done.** Write the `ALGZ` envelope + inner manifest as one normative specification (this

5. ✅ **Done.** Implement the Python reference encoder (`manage.py pack`) and a Python reference

## Required confirmations

Answering the review's explicit checklist directly, using the decisions merged above:

1. **Benchmark interpretation** — Confirmed: 290,961 B and 59.7:1 are the whole-corpus,
   single-frame, no-dictionary result. `AlgorithmDetails.algz` v1 will not embed a dictionary.
2. **Git preservation** — Confirmed: all hand-authored `description.md` files and all canonical
   `manage.py highlight` inputs remain tracked. Only the 1,080 generated per-language highlighted-Markdown
   files become gitignored (see Git migration for the exact `git rm --cached`/`.gitignore`/
   `.gitattributes` changes).
3. **Normative binary layout** — Provided above (Container format): a byte-accurate outer `ALGZ`
   envelope and inner `ADTL` manifest spec, with the Python emitter and Swift parser required to
   match it exactly field-for-field.
4. **Checksums** — The zstd content checksum is enabled and required (`write_checksum=True`,
   verified on decode). The outer SHA-256 is included (envelope flag bit 2) and covers the complete
   decompressed payload.
5. **Release safety** — Every range/size/version/UTF-8/dictionary/checksum condition uses a
   throwing release-mode check (Safety model, above); debug `assert`s are supplemental only, never
   the sole enforcement — this explicitly retracts the first draft's debug-only-assertion plan.
6. **Decoder completeness** — `ZstdKit` supports every normal literals and sequence encoding a
   standard compressor may emit (frame/block/literals/sequence completeness lists above);
   correctness does not depend on "what level 19 happens to produce."
7. **Dictionary capability** — Formatted and raw dictionary support is a generic `ZstdKit`
   capability, explicitly not required for `AlgorithmDetails.algz` v1 and safe to schedule as a
   separate milestone. A trained dictionary is documented as carrying pretrained entropy tables and
   initial repeat offsets, not merely raw history bytes.
8. **Unsafe-code policy** — The public API is safe Swift. Internal unsafe buffer access is
   permitted only inside `ZstdKit`'s optimized core (wildcopy, bit-reader refill), each instance
   documented with its bounds-check invariant and covered by differential tests; the outer
   envelope/manifest parser stays safe Swift.
9. **Performance plan** — Wide/SIMD copying, bit-reader optimization, four-stream Huffman
   interleaving, and downstream Markdown/`AttributedString` parsing are benchmarked as separate
   stages (Performance strategy, above), so decoder cost is never conflated with rendering cost.
10. **Memory policy** — The decompressed `Data` buffer is released once the retained
    `[String: ...]` model is built from it (or a lazy range-backed design replaces this if
    profiling supports it). Concurrent first-load callers share one in-flight decode via an
    actor or cached `Task`, never redundant parallel decompressions.
11. **Reproducibility** — The Python environment and compression settings are pinned via
    `pyproject.toml`/`uv.lock`; a developer verifies the committed archive matches tracked
    sources by re-running `uv run manage.py highlight && uv run manage.py pack` (self-verifies
    by default) and diffing (or via
    the migration plan's stale-archive check, step 17).
12. **Migration rollback** — The old loose-file loader stays in place until the application
    equivalence tests (Test strategy, above) pass byte-for-byte. If the pure-Swift decoder proves
    impractical, the DEFLATE/`Compression`-framework fallback (Contingency, above) reuses the same
    container, manifest, store, and Tuist wiring with only the `Codec` field and ratio changing.

## Part 2: Phase 12 stretch-goal effort analysis

Analysis only — no implementation in this pass. Source: `IMPLEMENTATION_PLAN.md` Phase 12 and
`ARCHITECTURE_V2.md` §2A.6 (same list, kept in sync deliberately, not two divergent plans). Ordered
least to most effort, using the concrete seams named in those docs and confirmed against current
code (`SortSession.swift`, `ReplayEngine.swift`, `RunControlBar.swift`).

### 1. Target-duration-based playback pacing — Small
`SortSession.swift:253` sets `replay.speed = settings.playbackSpeed` once per run inside
`startReplay(_:)`. `ReplayEngine.significantOperationCount` already exists and is tracked live
(surfaced today only as a displayed ops/sec stat in `RunControlBar.swift:131`). The core change is
close to one line: `replay.speed = significantOperationCount / targetDuration` at that same seed
point — sustained operation-apply throughput is already proven fine at the rates this would need,
so there's no perf risk. The real work is product/UI: a target-duration setting (replacing or
sitting alongside the existing speed slider) and deciding scope — global default vs. Showcase-mode
only — before writing it, since that decides whether `AppSettings` or a Showcase-specific type owns
the new value.

### 2. Binary tape export/import for a failed sort — Small-Medium
`Tape`/`TapeHeader`/`SortOperation` are already `Codable` (unused today), and `ReplayEngine`'s only
public initializer already takes a plain `Tape` with no opinion about provenance — import is nearly
free once export exists. The real work is a small versioned, tag-byte-per-case binary
encoder/decoder for `SortOperation` (a 12-case enum of small `Int` payloads) rather than reusing
`JSONEncoder`/`PropertyListEncoder`'s per-field overhead, plus a hook off
`SortSession.phase == .failed` to trigger the write, and a share-sheet/file-importer UI pair.
Self-contained — doesn't touch the renderer or replay logic.

### 3. CustomImage visualizer — Medium
Needs an image-picker UI (`PhotosPicker`, standard SwiftUI, low effort) and a per-pixel remap
design (array value/index → pixel position — ArrayV's own "Custom Image" concept).
`MetalShapeRenderer<Layout>` was already generalized across the other visualizer styles, so this
becomes a 15th conformance following an established pattern rather than new rendering
infrastructure. `ARCHITECTURE_V2.md` explicitly defers it "until the other 14 styles feel done and
this specific novelty is worth the cost" — a want-to-build-it-eventually item, not a blocked one.

### 4. Video/GIF export — Medium-Large
Per `ARCHITECTURE_V2.md`: iterate `tape.operations` off-screen at a fixed frame rate through
whichever `Visualizer` is selected, into `ImageRenderer` → `AVAssetWriter` — reusing the same
`VisualizationContext`/`draw(_:)` call the live UI already uses, driven by a loop instead of a
display link, rather than a bespoke offscreen Metal texture pipeline. That reuse lowers risk, but
this is genuinely unstarted (no `AVAssetWriter` usage anywhere in the repo today). Work: the
off-screen drive loop, frame-rate/frame-count math for large tapes, `AVAssetWriter` plumbing (pixel
buffer pool, video settings, session start/finish), and — only if true animated GIF is wanted —
`ImageIO`'s `CGImageDestination` animated-GIF path as a second encoder. Recommend scoping the first
pass to video-only to keep this Medium rather than Large.

### 5. Teaching-mode step annotations — Large
The engineering seam is small and already sketched: an optional `annotation: String?` (or a small
"step intent" enum) riding alongside `SortOperation`, surfaced by opt-in `Visualizer`s as
`DrawCommand.text` captions. The actual cost is content/design, not code —
`ARCHITECTURE_V2.md` sizes this as "a design pass at least as involved as this document" to design
a vocabulary of step intents meaningful across ~82 different algorithms (a compare in quicksort
means something different from a compare in radix sort). This is the only item where the blocker
is design work, not implementation — recommend doing it last, and treating it as its own separate
planning pass (prove the vocabulary on a handful of representative algorithms before rolling out to
all 82) rather than folding it into a general "implement stretch goals" pass.

### Suggested order

1 → 2 → 3 → 4 → 5, matching effort. All five are independent — consistent with
`IMPLEMENTATION_PLAN.md`'s own closing note that "none of these block each other" and should land
as separate commits, not a grab-bag. No dependency on Part 1 (compression) either — the two efforts
can proceed in any order relative to each other.
