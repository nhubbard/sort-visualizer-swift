Triangular Heap Sort is a variant of [Heapsort](https://en.wikipedia.org/wiki/Heapsort) that replaces the ordinary binary heap's implicit tree layout with a different one derived from the triangular numbers. An ordinary binary heap gives the node at index *i* two disjoint children at indices `2i + 1` and `2i + 2`, so the tree's branching factor is fixed at two and its height grows logarithmically with the number of elements. This variant instead imagines the array laid out as rows of a triangle: row 0 holds a single element, row 1 holds two, row 2 holds three, and so on, with row *r* starting at the triangular number `r(r + 1) / 2` and holding `r + 1` elements. A node's two children sit at the corresponding pair of positions in the next row down — and because each row is only one element wider than the row above it, neighboring nodes end up *sharing* a child with each other, the same overlapping adjacency found between adjacent rows of Pascal's triangle.

Aside from that difference in the parent-child mapping, the algorithm proceeds exactly like a standard heapsort. A "sift-down" operation holds a candidate value, repeatedly compares it against its (up to two) triangular children, and swaps it downward past any child that is strictly greater, stopping once it either has no children left to compare against or is already greater than both. Building the initial heap runs this sift-down bottom-up over every index of the array, and the sorting phase repeatedly swaps the heap's root — always the largest remaining value — out to the boundary of a shrinking heap and re-sifts what remains, exactly as in ordinary heapsort.

Because each row of the triangular structure is only one element wider than the last, the number of rows needed to hold *n* elements grows with the square root of *n* rather than with its logarithm — a much "flatter," wider tree than an ordinary binary heap of the same size. During the sorting phase, each extraction restarts its sift-down from the root, so a value can in principle travel across every row on its way back down, giving each extraction a cost proportional to the square root of the current heap's size rather than its logarithm. Repeated over all *n* extractions, this makes Triangular Heap Sort's running time proportional to *n* times the square root of *n*, noticeably worse than the *n* log *n* bound of an ordinary binary heapsort, despite superficially looking like just another heap-based selection sort.

Because the sorting phase's extraction loop only ever finishes fully sorting the two smallest remaining elements once they have been explicitly swapped into place, one special case has to be handled outside the main loop: once the heap has shrunk down to exactly two elements, those two are left sitting in "largest first" heap order rather than ascending sorted order, and a final explicit comparison-and-swap of the first two positions is needed to put them the right way around. Like ordinary Heapsort, Triangular Heap Sort is not a stable sort — the repeated swapping used both to build the heap and to extract its root can freely reorder equal elements relative to one another — and it sorts in place using only a constant amount of extra bookkeeping beyond the array itself.
