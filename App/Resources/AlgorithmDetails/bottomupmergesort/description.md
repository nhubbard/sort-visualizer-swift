*From Wikipedia, the free encyclopedia*

Bottom-up Merge Sort is an iterative variant of [Merge Sort](https://en.wikipedia.org/wiki/Merge_sort) that avoids recursion entirely. Rather than dividing the array in half over and over until reaching single elements, it starts from the opposite end: it treats every single element as an already-sorted run of length one, then repeatedly merges adjacent runs into progressively longer sorted runs — first pairs of length 1 into runs of length 2, then pairs of length 2 into runs of length 4, and so on, doubling the run width on each pass until a single pass merges the whole array.

Because it works its way up from the smallest runs instead of down from the whole array, this approach is often called bottom-up (or iterative) merge sort, in contrast to the classic top-down recursive formulation. It produces exactly the same result and shares the same asymptotic time and space bounds, but it never grows a call stack, which matters in environments where recursion is expensive, restricted, or unavailable — embedded systems, kernel code, and older compilers without reliable tail-call optimization are typical examples.

The one wrinkle bottom-up merge sort has to handle that the recursive version gets for free is an array length that isn't a power of two: the final run in a given pass may be shorter than the target width, or may have no partner run to merge with at all. A correct implementation clamps each run's boundaries to the end of the array and simply carries a short leftover run forward untouched to the next pass, where it eventually gets merged in like any other run.

Like its recursive counterpart, Bottom-up Merge Sort is a stable [comparison sort](https://en.wikipedia.org/wiki/Comparison_sort): equal elements never cross past one another during a merge, so their relative order is preserved. It also still requires an auxiliary buffer the size of the input array to hold each pass's merged output before it is copied back, so it is not an in-place algorithm.
