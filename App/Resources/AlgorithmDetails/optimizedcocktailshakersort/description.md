Optimized Cocktail Shaker Sort applies the same refinement [Optimized Bubble Sort](https://en.wikipedia.org/wiki/Bubble_sort) makes to plain [Bubble Sort](https://en.wikipedia.org/wiki/Bubble_sort) — but to [Cocktail Shaker Sort](https://en.wikipedia.org/wiki/Cocktail_shaker_sort), its bidirectional counterpart. Plain Cocktail Shaker Sort shrinks its unsorted window by exactly one element at each end per full forward-and-backward pass, even when a much larger stretch at either end is already known to be sorted. This variant instead tracks, during each sweep, how many consecutive comparisons did *not* require a swap, and shrinks that end of the window by the full length of that trailing sorted run instead of by one.

Each outer iteration still does the same two sweeps as plain Cocktail Shaker Sort: a forward pass carrying the largest remaining value toward the high end, followed by a backward pass carrying the smallest remaining value toward the low end. What changes is the bookkeeping around each sweep. A counter starts at one and increments every time a comparison does *not* trigger a swap; it resets to one the moment a swap does happen. Once a sweep finishes, its end of the window moves inward by the counter's final value, so any consecutive run of already-sorted elements found during that sweep is skipped entirely on the next pass — in either direction.

Because a sweep that makes no swaps at all means its counter reaches the full width still being scanned, this optimization also causes the loop to terminate in a single forward-and-backward pass on an already-sorted array, giving it the same O(n) best case as Optimized Bubble Sort and plain Cocktail Shaker Sort. On randomly ordered or reverse-ordered input the counters rarely grow past one or two, so average and worst-case behavior remains O(n^2), identical to the unoptimized algorithm.

Like plain Cocktail Shaker Sort, this variant only ever swaps a pair when the earlier element compares strictly greater than the later one, so equal elements are never exchanged and the algorithm remains a stable sort. It sorts in place and requires no auxiliary storage beyond a handful of loop counters.
